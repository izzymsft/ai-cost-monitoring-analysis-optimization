## 1. Understanding Token Costs

Claude Code charges by API token consumption. Costs vary significantly based on:

- **Model selection** — Opus costs more than Sonnet or Haiku
- **Codebase size** — larger codebases mean larger contexts per request
- **Usage patterns** — running multiple instances or automation amplifies spend
- **Extended thinking** — thinking tokens are billed as output tokens and can reach tens of thousands per request

### Typical Cost Ranges (API users)

| Scenario | Cost |
|---|---|
| Average per developer per active day | ~$13 |
| Average per developer per month | $150–$250 |
| 90th percentile per active day | Under $30 |

> **Note:** For subscription plans (Pro, Max, Team, Enterprise), see [claude.com/pricing](https://claude.com/pricing). The session cost figure in `/usage` is only relevant for API users, not subscribers.

### Token Types

Every API request produces four token types, each with different cost implications:

| Token Type | Description |
|---|---|
| `input` | Tokens sent to the model (your prompts, context, files) |
| `output` | Tokens generated by the model (responses, code) |
| `cacheRead` | Tokens served from prompt cache (significantly cheaper) |
| `cacheCreation` | Tokens written to the prompt cache |

Claude Code automatically uses **prompt caching** to reduce costs for repeated content like system prompts. Cache reads are much cheaper than fresh input tokens.


Based on the [pricing page](https://platform.claude.com/docs/en/about-claude/pricing#model-pricing), here are all the token types you can be billed for:

**Standard Token Types**

**Base Input Tokens** — Standard tokens sent to the model in your request (system prompt, conversation history, documents, etc.)

**Output Tokens** — Tokens generated by the model in its response.

**Prompt Caching Token Types**

There are three cache-related token categories:
- **5-minute Cache Writes** — Charged at 1.25x the base input price; cache stays valid for 5 minutes
- **1-hour Cache Writes** — Charged at 2x the base input price; cache valid for 1 hour
- **Cache Hits & Refreshes** — Charged at 0.1x (10%) of the base input price when a subsequent request reads from cache

**Tool-Related Tokens**

Tool use adds extra tokens from the `tools` parameter definitions, `tool_use` content blocks, `tool_result` content blocks, and an automatic system prompt added by the API to enable tool use. Specific tools carry fixed overhead — for example, the bash tool adds 245 input tokens, the text editor tool adds 700 tokens, and computer use adds 735 tokens per tool definition.

**Non-Token Billing (worth knowing)**

Beyond tokens, a couple of features are billed differently:
- **Web search** is charged at $10 per 1,000 searches, in addition to standard token costs for search-generated content.
- **Code execution** is billed by execution time at $0.05 per container-hour beyond a free 1,550 hours/month — though it's free when used alongside web search or web fetch.
- **Claude Managed Agents** adds a **session runtime** charge of $0.08 per session-hour, on top of standard token costs.

So in summary, the five core token billing categories are: **base input, output, 5m cache writes, 1h cache writes, and cache reads/refreshes** — with tool tokens counted as part of input tokens.

## 2. Tracking Your Costs

### In-Session: The `/usage` Command

Run `/usage` at any time to see a live breakdown of the current session:

```
Total cost:            $0.55
Total duration (API):  6m 19.7s
Total duration (wall): 6h 33m 10.2s
Total code changes:    0 lines added, 0 lines removed
```

The cost shown is a **local estimate** computed from token counts. For authoritative billing, use the [Claude Console usage page](https://platform.claude.com/usage).

You can also configure your **status line** to display token usage continuously without running `/usage` manually.

### Background Token Consumption

Even when idle, Claude Code uses a small number of tokens for:

- Conversation summarization (for `--resume` functionality)
- Command processing (e.g., `/usage` status checks)

This typically costs **under $0.04 per session**.

## 3. Managing Costs for Teams

### Workspace Spend Limits (API customers)

Administrators can set a **workspace spend limit** on the "Claude Code" workspace in the [Claude Console](https://platform.claude.com). This caps total Claude Code spend for your organization.

> When you first authenticate Claude Code with your Console account, a "Claude Code" workspace is automatically created. API keys cannot be created for this workspace — it exists solely for Claude Code authentication and usage tracking.

To protect other production workloads, you can also set a **workspace rate limit** so Claude Code does not consume your entire organization's API quota.

### Rate Limit Recommendations

Setting per-user Token Per Minute (TPM) and Request Per Minute (RPM) limits prevents runaway usage. Recommended values by team size:

| Team Size | TPM per User | RPM per User |
|---|---|---|
| 1–5 users | 200k–300k | 5–7 |
| 5–20 users | 100k–150k | 2.5–3.5 |
| 20–50 users | 50k–75k | 1.25–1.75 |
| 50–100 users | 25k–35k | 0.62–0.87 |
| 100–500 users | 15k–20k | 0.37–0.47 |
| 500+ users | 10k–15k | 0.25–0.35 |

These limits apply at the **organization level**, not per individual user. Individuals can temporarily exceed their share when others are inactive. Plan for higher limits if you run live training sessions with large concurrent groups.

### Agent Teams: Special Cost Considerations

Agent teams spawn multiple Claude Code instances, each with its own context window. Token usage scales roughly proportionally with team size.

Best practices for agent team cost control:

- **Use Sonnet for teammates** — it balances capability and cost for coordination tasks
- **Keep teams small** — each teammate runs its own full context window
- **Write focused spawn prompts** — teammates auto-load CLAUDE.md, MCP servers, and skills, so every byte in the spawn prompt adds to their starting context
- **Clean up teams when done** — active teammates continue consuming tokens even when idle
- **Be aware**: agent teams use approximately 7× more tokens than standard sessions when running in plan mode

### Bedrock, Vertex, and Foundry

Claude Code does not send cost metrics from cloud provider deployments. For spend tracking in these environments, consider [LiteLLM](https://docs.litellm.ai/docs/proxy/virtual_keys#tracking-spend), an open-source proxy that tracks spend by key (unaffiliated with Anthropic, not security-audited).

## 4. Reducing Token Usage

Context size is the primary cost driver. The following strategies minimize unnecessary context and reduce per-message costs.

### Manage Context Proactively

- **Clear between unrelated tasks** — Use `/clear` when switching to a new topic. Use `/rename` before clearing so you can find the session later with `/resume`.
- **Add compaction instructions** — When running `/compact`, specify what to preserve: `/compact Focus on code samples and API usage`. You can also set default compaction behavior in your CLAUDE.md:

```markdown
# Compact instructions
When you are using compact, please focus on test output and code changes.
```

- **Keep CLAUDE.md under 200 lines** — It loads into every session. Move workflow-specific instructions (PR reviews, migration guides) into **skills** that load on demand instead.

### Choose the Right Model

- **Sonnet** handles most coding tasks well and costs less than Opus
- **Opus** is worth the cost for complex architectural decisions or multi-step reasoning
- **Haiku** is suitable for simple subagent tasks

Switch models mid-session with `/model`, set a default in `/config`, or specify `model: haiku` in subagent configuration.

### Reduce MCP Server Overhead

MCP tool definitions are deferred by default — only tool names enter context until Claude actually uses a specific tool. To minimize overhead further:

- Prefer CLI tools (`gh`, `aws`, `gcloud`) when available — they don't add per-tool definitions to context
- Disable unused MCP servers with `/mcp`
- Run `/context` to see what is currently consuming context space

### Offload Processing with Hooks

Hooks preprocess data before it reaches Claude's context. A hook that greps a 10,000-line log file for `ERROR` and returns only matching lines reduces context from tens of thousands of tokens to hundreds.

Example hook that filters test output to show only failures:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "~/.claude/hooks/filter-test-output.sh"
          }
        ]
      }
    ]
  }
}
```

### Move Workflow Instructions to Skills

Skills load on demand, keeping your base context small. Move detailed instructions for specific workflows out of CLAUDE.md and into skills. A "codebase-overview" skill can give Claude project structure knowledge immediately, replacing expensive multi-file exploration.

### Adjust Extended Thinking

Extended thinking is enabled by default and significantly improves performance on complex tasks, but it can cost tens of thousands of tokens per request. For simpler tasks:

- Lower the effort level with `/effort` or in `/model`
- Disable thinking in `/config`
- Set a lower budget: `MAX_THINKING_TOKENS=8000`

### Use Plan Mode for Complex Tasks

Press **Shift+Tab** to enter plan mode before implementation. Claude explores the codebase and proposes an approach for your approval, preventing expensive re-work from heading in the wrong direction.

Other habits that reduce wasted tokens:

- Press **Escape** to stop Claude immediately if it's heading the wrong way
- Use `/rewind` or double-tap Escape to restore to a previous checkpoint
- Give Claude verification targets (test cases, screenshots, expected output) so it catches issues before you need to request fixes
- Test incrementally — write one file, test it, then continue

### Delegate Verbose Operations to Subagents

Running tests, fetching documentation, or processing large log files can pollute your main context. Delegate these to subagents so verbose output stays isolated in the subagent's context, with only a summary returned to your main conversation.

### Write Specific Prompts

Vague prompts trigger broad scanning. Specific prompts let Claude work efficiently with minimal file reads:

| Instead of... | Try... |
|---|---|
| "Improve this codebase" | "Add input validation to the login function in auth.ts" |
| "Fix the tests" | "Fix the failing assertion in UserService.test.ts line 42" |

## 5. Monitoring Team Usage with OpenTelemetry

Claude Code exports real-time telemetry via OpenTelemetry (OTel), enabling full observability into usage, costs, and activity across your organization.

### Quick Start

```bash
# 1. Enable telemetry
export CLAUDE_CODE_ENABLE_TELEMETRY=1

# 2. Choose exporters
export OTEL_METRICS_EXPORTER=otlp
export OTEL_LOGS_EXPORTER=otlp

# 3. Configure your collector endpoint
export OTEL_EXPORTER_OTLP_PROTOCOL=grpc
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317

# 4. Set authentication if required
export OTEL_EXPORTER_OTLP_HEADERS="Authorization=Bearer your-token"
```

> Default export intervals are 60 seconds for metrics and 5 seconds for logs. Use shorter intervals (e.g., `OTEL_METRIC_EXPORT_INTERVAL=10000`) while setting up, and reset to defaults for production.

### Centralized Admin Configuration

Administrators can deploy telemetry settings to all users via the managed settings file, preventing users from overriding them:

```json
{
  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "OTEL_METRICS_EXPORTER": "otlp",
    "OTEL_LOGS_EXPORTER": "otlp",
    "OTEL_EXPORTER_OTLP_PROTOCOL": "grpc",
    "OTEL_EXPORTER_OTLP_ENDPOINT": "http://collector.example.com:4317",
    "OTEL_EXPORTER_OTLP_HEADERS": "Authorization=Bearer example-token"
  }
}
```

Distribute via MDM or other device management tooling. Environment variables in managed settings have high precedence and cannot be overridden by users.

### Key Metrics to Track

| Metric | Description | Useful For |
|---|---|---|
| `claude_code.cost.usage` | Estimated cost per API request (USD) | Spend tracking by user, team, model |
| `claude_code.token.usage` | Token counts by type | Input/output/cache breakdown |
| `claude_code.session.count` | Sessions started | Adoption and engagement trends |
| `claude_code.lines_of_code.count` | Lines added/removed | Productivity measurement |
| `claude_code.commit.count` | Git commits created | Development workflow impact |
| `claude_code.pull_request.count` | PRs created | Development workflow impact |
| `claude_code.active_time.total` | Active usage time in seconds | Actual engagement vs. idle |

The `claude_code.cost.usage` and `claude_code.token.usage` metrics include rich attribution attributes: `model`, `query_source`, `agent.name`, `skill.name`, and `plugin.name`, enabling granular cost attribution.

> Cost metrics are approximations. For official billing data, use your API provider (Claude Console, Amazon Bedrock, or Google Cloud Vertex).

### Multi-Team Attribution

Add custom attributes to distinguish between teams or cost centers:

```bash
export OTEL_RESOURCE_ATTRIBUTES="department=engineering,team.id=platform,cost_center=eng-123"
```

This enables per-team dashboards, cost center attribution, and team-specific alerts. Note the formatting requirements:
- No spaces in values (use underscores or camelCase)
- Comma-separated `key=value` pairs only
- Special characters must be percent-encoded

### Managing Metrics Cardinality

High-cardinality attributes increase storage costs and reduce query performance. Use these controls to tune your metrics:

| Variable | Default | Effect |
|---|---|---|
| `OTEL_METRICS_INCLUDE_SESSION_ID` | `true` | Per-session granularity; set to `false` to reduce cardinality |
| `OTEL_METRICS_INCLUDE_ACCOUNT_UUID` | `true` | Per-user attribution; disable if not needed |
| `OTEL_METRICS_INCLUDE_VERSION` | `false` | Enable to track metrics by Claude Code version |

### Distributed Tracing (Beta)

Enable distributed tracing to see full request waterfalls linking each user prompt to the API calls and tool executions it triggers:

```bash
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1
export OTEL_TRACES_EXPORTER=otlp
```

Trace spans are organized hierarchically:

```
claude_code.interaction
├── claude_code.llm_request
├── claude_code.hook
└── claude_code.tool
    ├── claude_code.tool.blocked_on_user
    └── claude_code.tool.execution
```

### Privacy Controls for Telemetry

By default, Claude Code redacts sensitive content from telemetry. Opt in explicitly to capture additional detail:

| Variable | What it exposes |
|---|---|
| `OTEL_LOG_USER_PROMPTS=1` | User prompt content |
| `OTEL_LOG_TOOL_DETAILS=1` | Bash commands, MCP server/tool names, file paths, tool input arguments |
| `OTEL_LOG_TOOL_CONTENT=1` | Full tool input/output content (truncated at 60 KB) |
| `OTEL_LOG_RAW_API_BODIES=1` | Full API request/response JSON including conversation history |

Only enable these when genuinely needed and ensure your telemetry backend filters or redacts sensitive values appropriately.

### Recommended Backend Choices

| Signal | Good Options |
|---|---|
| Metrics | Prometheus, ClickHouse, Datadog, Honeycomb |
| Logs/Events | Elasticsearch, Loki, ClickHouse, Datadog |
| Traces | Jaeger, Grafana Tempo, Honeycomb, Datadog |

For DAU/WAU/MAU calculations, prioritize backends with efficient unique-value query support.

## 6. Team Analytics Dashboard

### Access by Plan

| Plan | Dashboard URL | Features |
|---|---|---|
| Teams / Enterprise | [claude.ai/analytics/claude-code](https://claude.ai/analytics/claude-code) | Usage metrics, GitHub contribution metrics, leaderboard, CSV export |
| API (Console) | [platform.claude.com/claude-code](https://platform.claude.com/claude-code) | Usage metrics, spend tracking, per-user insights |

### Teams / Enterprise Dashboard

Admins and Owners can access the full dashboard, which includes:

**Usage metrics**
- Lines of code accepted
- Suggestion accept rate
- Daily active users and sessions

**Contribution metrics** (requires GitHub integration)
- PRs containing Claude Code-assisted code
- Lines of code shipped with Claude Code assistance
- Percentage of all PRs with Claude Code involvement

**Leaderboard** — top 10 contributors ranked by usage volume, with CSV export for all users

#### Setting Up GitHub Integration

1. A GitHub admin installs the [Claude GitHub app](https://github.com/apps/claude) on your organization's GitHub account
2. A Claude Owner navigates to [claude.ai/admin-settings/claude-code](https://claude.ai/admin-settings/claude-code) and enables Claude Code analytics
3. Enable the "GitHub analytics" toggle on the same page
4. Complete the GitHub authentication flow and select which organizations to include

Data typically appears within 24 hours and updates daily. GitHub Cloud and GitHub Enterprise Server are both supported.

> Contribution metrics are not available for organizations with Zero Data Retention enabled.

#### How PR Attribution Works

PRs are tagged as "with Claude Code" when they contain at least one line of code written during a Claude Code session. Attribution is deliberately conservative — only high-confidence matches are counted.

Key details:
- Sessions from 21 days before to 2 days after the PR merge date are considered
- Auto-generated files (lock files, build artifacts, minified code, test fixtures) are excluded
- Code rewritten by developers with more than 20% difference is not attributed to Claude Code
- Attributed PRs are labeled `claude-code-assisted` in GitHub, enabling programmatic querying

#### Using Analytics Effectively

**Monitor adoption** — Track the Adoption chart to identify active users who can share best practices, and dips in usage that may indicate friction.

**Measure ROI** — Track changes in PRs per user over time as adoption increases. Pair with DORA metrics or sprint velocity for a fuller picture.

**Find power users** — The Leaderboard surfaces team members who can share prompting techniques, workflows, and help onboard others.

**Access data programmatically** — Search GitHub for PRs labeled `claude-code-assisted` to build custom reports.

### API / Console Dashboard

API customers access analytics at [platform.claude.com/claude-code](https://platform.claude.com/claude-code) (requires UsageView permission).

The Console dashboard shows:
- Lines of code accepted
- Suggestion accept rate
- Daily active users and sessions (chart)
- Daily API spend (chart)

**Team insights table** shows per-user data:
- All users who have authenticated (API key users by key identifier, OAuth users by email)
- Spend this month
- Lines accepted this month

> Spend figures in the Console dashboard are estimates for analytics purposes. For actual billing, refer to your billing page.

## 7. Security and Privacy Considerations

### Telemetry is Opt-In

OTel export to your backend requires explicit configuration via `CLAUDE_CODE_ENABLE_TELEMETRY=1`. Anthropic's separate operational telemetry is a distinct system — see the [data usage documentation](https://code.claude.com/docs/en/data-usage) for details on disabling it.

### What is Never Collected by Default

- Raw file contents or code snippets
- User prompt content (only prompt length is recorded)
- Tool input arguments and parameters
- Tool input/output content in trace spans
- Raw API request/response bodies

### User Identity in Telemetry

When authenticated via OAuth, `user.email` is included in all telemetry attributes. If this is a concern, configure your telemetry backend to filter or redact this field.

For API key–based authentication (or Bedrock/Vertex/Foundry), no Claude account identity is populated. Attach user identity manually via `OTEL_RESOURCE_ATTRIBUTES`:

```bash
export OTEL_RESOURCE_ATTRIBUTES="enduser.id=jdoe@example.com,enduser.directory_id=S-1-5-21-..."
```

### Audit Capabilities

OTel events function as an audit log for Claude Code activity. Every event includes identity attributes tying tool calls, MCP activity, and permission decisions to the user who triggered them. To send events to a SIEM:

```json
{
  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "OTEL_LOGS_EXPORTER": "otlp",
    "OTEL_LOG_TOOL_DETAILS": "1",
    "OTEL_EXPORTER_OTLP_LOGS_PROTOCOL": "http/protobuf",
    "OTEL_EXPORTER_OTLP_LOGS_ENDPOINT": "https://siem.example.com:4318/v1/logs",
    "OTEL_EXPORTER_OTLP_HEADERS": "Authorization=Bearer your-siem-token"
  }
}
```

Key security signals to monitor:

| Signal | Event | Key Attributes |
|---|---|---|
| Tool call allowed or denied | `tool_decision` | `decision`, `source`, `tool_name` |
| Permission mode escalation | `permission_mode_changed` | `from_mode`, `to_mode`, `trigger` |
| Login/logout/auth failure | `auth` | `action`, `success`, `error_category` |
| MCP server connect/failure | `mcp_server_connection` | `status`, `server_name`, `error_code` |
| Plugin installed and source | `plugin_installed` | `plugin.name`, `marketplace.name` |
| Commands run and files touched | `tool_result` + `OTEL_LOG_TOOL_DETAILS=1` | `tool_parameters`, `tool_input` |
